PARTE 1

Activities

A unidade básica de interface do Android

O que é uma Activity?

Uma Activity é um componente Android que geralmente representa uma tela ou uma área de interação com o usuário.

  • ▸A maioria dos apps com interface gráfica possui pelo menos uma Activity — mas ela é só um dos componentes possíveis (existem também Service, BroadcastReceiver, ContentProvider...).
  • ▸Um app pode ter várias Activities: uma tela de login, uma de lista, uma de detalhes...
  • ▸Cada Activity precisa ser declarada no AndroidManifest.xml para existir.
  • ▸Nos nossos exemplos, uma Activity será uma classe Java que estende AppCompatActivity.
Relembrando a Aula 1: nosso contador de cliques já possui uma Activity — a MainActivity.

Simulação: montando uma Activity

Adicione componentes ao layout e veja o XML e o Java sendo gerados ao vivo — a mesma dupla XML ↔ código que você vai escrever no Android Studio.

Adicionar View:

Activity ↔ Layout: a ligação

No modelo tradicional baseado em Views, a Activity não desenha a tela sozinha — ela carrega um layout XML e passa a controlá-lo.

📄 activity_main.xml

Define a interface: botões, textos, posições
⇄

☕ MainActivity.java

Define o comportamento: cliques, lógica, dados
@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);

    setContentView(R.layout.activity_main);
    // carrega o layout XML e o define como conteúdo da Activity
}
setContentView(): carrega o layout e o define como conteúdo visual da Activity. No Jetpack Compose isso muda — não há XML nem setContentView(); usa-se setContent { ... }.

Simulação: setContentView() e findViewById()

Acompanhe o que acontece na memória RAM quando o layout é inflado, e como o código encontra cada componente.

public class MainActivity extends AppCompatActivity {
    TextView tvTitulo;
    Button btnEntrar;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);

        tvTitulo = findViewById(R.id.tvTitulo);
        btnEntrar = findViewById(R.id.btnEntrar);
    }
}

Declarando a Activity no Manifest

Toda Activity precisa aparecer em AndroidManifest.xml — é assim que o sistema Android sabe que ela existe:

<application ... >
    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity>
</application>
  • ▸MAIN + LAUNCHER: marca esta Activity como o ponto de entrada pelo launcher (ícone do app na tela inicial).
  • ▸Esse intent-filter não é obrigatório em toda Activity — todas precisam estar declaradas em <activity>, mas normalmente só uma recebe MAIN + LAUNCHER.
App
 ├─ MainActivity ← MAIN + LAUNCHER
 ├─ LoginActivity
 └─ DetalhesActivity

PARTE 2

Layouts em XML

Organizando componentes visuais na tela

Views e ViewGroups

  • ▸View: um componente visual individual — TextView, Button, ImageView, EditText...
  • ▸ViewGroup: um contêiner que organiza outras Views (inclusive outros ViewGroups) — é um layout.
  • ▸Todo layout XML tem uma ViewGroup raiz que define como os filhos são posicionados.
Pense na tela como uma árvore: a ViewGroup raiz é o tronco, e cada View ou sub-layout é um galho.

Principais tipos de Layout

LinearLayout

  • Organiza filhos em uma linha, horizontal ou vertical
  • Simples e previsível
  • Fica lento com telas complexas (hierarquias aninhadas)

ConstraintLayout

  • Posiciona Views por restrições (constraints) relativas umas às outras ou ao pai
  • Hierarquia mais achatada — melhor performance
  • Template padrão do Android Studio ("Empty Views Activity")

Existem outros: FrameLayout (empilha views), RelativeLayout (mais antigo, similar ao ConstraintLayout).

ConstraintLayout na prática

O layout do nosso contador de cliques usa constraints para centralizar o texto na tela:

<TextView
    android:id="@+id/tvShowContador"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    app:layout_constraintTop_toTopOf="parent"
    app:layout_constraintBottom_toBottomOf="parent"
    app:layout_constraintStart_toStartOf="parent"
    app:layout_constraintEnd_toEndOf="parent" />
  • ▸constraintTop_toTopOf="parent" — prende o topo da View ao topo do pai.
  • ▸As 4 constraints juntas centralizam a View, tanto horizontal quanto verticalmente.
  • ▸Sem constraint em algum lado, a View "flutua" sem posição definida — erro comum de quem está começando.

PARTE 3

Ciclo de Vida da Activity

Do nascimento à destruição: os 7 callbacks fundamentais

Por que existe um ciclo de vida?

Um celular é diferente de um computador: chamadas chegam, o usuário troca de app, a bateria acaba, a tela gira. O Android precisa de um jeito de avisar sua Activity quando cada uma dessas coisas acontece.

  • ▸Liberar recursos (câmera, sensores, conexões) quando o app não está visível.
  • ▸Salvar dados antes que o sistema mate o processo por falta de memória.
  • ▸Retomar o estado exatamente de onde o usuário parou.
O Android chama métodos específicos — os callbacks do ciclo de vida — em cada uma dessas transições. Sobrescrevê-los é como o app "escuta" essas mudanças.

Os 7 callbacks

Fonte: developer.android.com/guide/components/activities/activity-lifecycle. Fluxo típico: onCreate → onStart → onResume (visível e interativa) → onPause → onStop (some de vista) → onDestroy ou onRestart → onStart (volta).

Simulação: dispare os eventos, veja o ciclo reagir

Clique nas ações do sistema (abrir, Home, trocar de app, Voltar, girar a tela) e observe qual estado é alcançado e quais callbacks são chamados, na ordem — o mesmo diagrama clássico do ciclo de vida, agora ao vivo.

Estado atual: Activity ainda não existe
Callbacks chamados

onCreate() e onDestroy()

onCreate()

  • Chamado uma única vez quando a Activity é criada
  • Local do setContentView(), findViewById(), inicialização de variáveis
  • Recebe savedInstanceState — útil para restaurar estado salvo

onDestroy()

  • Última chamada antes da Activity deixar de existir
  • Chamado ao fechar o app (finish()) ou quando o sistema recria a Activity (ex.: rotação de tela)
  • Local para liberar recursos que não devem vazar
Pegadinha comum: girar a tela chama onDestroy() seguido de um novo onCreate() — a Activity é recriada do zero, e variáveis não salvas se perdem.

onPause(), onResume(), onStop()

  • ▸onPause(): a Activity perde o foco, mas ainda pode estar parcialmente visível (ex.: um diálogo aberto por cima). Deve ser rápido — pausar animações, sensores.
  • ▸onResume(): a Activity volta a ficar em primeiro plano e interativa. Retomar o que foi pausado.
  • ▸onStop(): a Activity fica completamente invisível (outro app cobriu a tela, ou o usuário apertou Home). Bom lugar para liberar recursos pesados.
onPause() é sempre chamado antes de onStop() — mas nem todo onPause() é seguido de onStop() (ex.: um diálogo transparente por cima não esconde a Activity totalmente).

Cenário 2 — Botão Home / trocar de app

→
onStop

A Activity não é destruída — fica parada em segundo plano, mantendo seu estado em memória.

Ao voltar para o app:

onRestart
→
onStart
→
onResume
Aqui o contador mantém o valor — a instância da Activity nunca foi destruída, só pausada.

Cenário 3 — Botão Voltar (fechar a tela)

onPause
→
onStop
→
onDestroy

O usuário decidiu sair da tela — a Activity é destruída de forma definitiva (diferente da rotação, aqui não vem um onCreate() automático depois).

Se o usuário abrir o app de novo, uma nova instância da Activity é criada do zero, com onCreate() chamado sem estado salvo anterior.

PARTE 4

Como um App Nasce

Do toque no ícone ao primeiro processo rodando o seu código

Do boot do sistema até o primeiro app

Antes de qualquer app abrir, o sistema já passou por boot ROM, bootloader, kernel Linux, init e os serviços nativos (visto na Aula 1). O Zygote nasce nessa etapa — e é ele quem gera cada app.

Zygote e a Android Runtime

O Zygote é um processo especial, criado ainda durante o boot, que já vem com a Android Runtime (ART) e as classes principais do framework pré-carregadas na memória.

Ele funciona como um "molde": em vez de iniciar cada app do zero, o sistema faz um fork() do Zygote — muito mais rápido do que carregar tudo de novo a cada app aberto.

O que acontece ao tocar no ícone?

O toque dispara uma Intent no sistema, com os dados de qual aplicação deve ser iniciada — direcionada ao ActivityManager, serviço do Android Framework:

Intent
package: "com.ifsc.contaclick"
type: Intent.ACTION_MAIN
category: Intent.CATEGORY_LAUNCHER
class: com.ifsc.contaclick.MainActivity.class
↓
ActivityManager
O ActivityManager verifica as permissões da Intent e, se puder iniciar o app, faz um fork() do processo Zygote.

Do fork() ao processo do seu app

O novo processo nasce como uma cópia do Zygote, já com a ART pronta, e recebe um PID (Process ID) próprio:

PID = 1013 · GUID = 1013

➜

ApplicationContext

  • ▸O código do app (.dex) é carregado dentro desse novo processo.
  • ▸É criado o ApplicationContext — o objeto que dá acesso a recursos, preferências e serviços do sistema.
  • ▸Só depois disso o ActivityManager chama o onCreate() da sua MainActivity.

Copy-on-Write: por que o fork() é tão rápido?

Cada app iniciado é um processo filho do Zygote, mas eles não duplicam toda a memória — reutilizam o espaço já carregado pelo processo pai:

Copy-on-Write (COW): cada processo filho só grava em memória própria a partir do momento em que modifica algo — até lá, todos compartilham a mesma região de memória do processo pai. É por isso que abrir um novo app é rápido e econômico em memória.

Na Prática

Observando o ciclo de vida no contador de cliques e salvando estado

Enxergando o ciclo de vida com Log

A forma mais direta de ver os callbacks acontecendo é logar cada um e observar no Logcat (visto na Aula 1):

private static final String TAG = "LifecycleDemo";

@Override protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    Log.d(TAG, "onCreate");
}
@Override protected void onStart()   { super.onStart();   Log.d(TAG, "onStart"); }
@Override protected void onResume()  { super.onResume();  Log.d(TAG, "onResume"); }
@Override protected void onPause()   { super.onPause();   Log.d(TAG, "onPause"); }
@Override protected void onStop()    { super.onStop();    Log.d(TAG, "onStop"); }
@Override protected void onDestroy() { super.onDestroy(); Log.d(TAG, "onDestroy"); }
Rode o app, gire o celular, aperte Home e Voltar — e veja no adb logcat a sequência exata de callbacks de cada cenário da Parte 3.

Salvando estado: onSaveInstanceState()

Para o contador sobreviver à rotação de tela, salvamos seu valor antes da Activity ser destruída:

@Override
protected void onSaveInstanceState(@NonNull Bundle outState) {
    super.onSaveInstanceState(outState);
    outState.putInt("contador", contador); // salva antes de destruir
}
@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);
    tvShowContador = findViewById(R.id.tvShowContador);

    if (savedInstanceState != null) {
        contador = savedInstanceState.getInt("contador", 0); // restaura
    }
    tvShowContador.setText(String.valueOf(contador));
}

Quando o Bundle salva (e quando não salva)

  • ▸onSaveInstanceState() é chamado antes de onStop(), quando o sistema pode recriar a Activity (rotação, app em segundo plano sob pressão de memória).
  • ▸Não é chamado quando o usuário aperta Voltar ou o app é fechado explicitamente — nesses casos, o usuário indicou que quer sair, não continuar depois.
  • ▸Serve para dados pequenos e temporários de UI (posição de scroll, texto digitado, contador). Não é substituto de um banco de dados.
Para persistir dados entre execuções completas do app (não só rotações), a ferramenta certa é SharedPreferences ou um banco local — assunto de uma próxima aula.

Recapitulando

  • ▸Uma Activity é uma tela; ela infla um layout XML com setContentView() e é declarada no AndroidManifest.xml.
  • ▸ConstraintLayout organiza Views por restrições relativas, com hierarquia mais achatada que o LinearLayout.
  • ▸O ciclo de vida tem 7 callbacks: onCreate, onStart, onResume, onPause, onStop, onDestroy e onRestart.
  • ▸Girar a tela destrói e recria a Activity; Home apenas pausa; Voltar destrói definitivamente.
  • ▸onSaveInstanceState() salva dados de UI temporários para sobreviver a recriações do sistema.
