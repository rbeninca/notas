PARTE 1

Contextualização, História e Motivação

De onde o Git veio — e por que ele resolve um problema real

O problema no tempo: sozinho já é difícil

Mesmo trabalhando sozinho, manter o controle das versões de um arquivo ao longo de dias, meses e anos vira uma bagunça:

Dia 1📄trabalho.txt
Dia 12📄trabalho_v2.txt
Mês 2📄trabalho_final.txt
Mês 5📄trabalho_final2.txt
Ano 1📄trabalho_final_definitivo.txt
Ano 2📄trabalho_final_AGORA_SIM.txt
Qual desses é a versão certa? O que mudou entre eles? Dá para voltar ao que existia há 6 meses?

O problema piora em equipe — e em times distribuídos

Agora imagine quatro pessoas, em cidades diferentes, cada uma com sua própria cópia do mesmo arquivo — sem nenhuma coordenação entre elas:

São Paulo
+ validação de login
Berlim
+ tratamento de erro
Toronto
+ validação de item
Tóquio
+ logout automático
Cada um alterou o mesmo arquivo de um jeito diferente. Quem está com a versão "boa"? Como juntar tudo isso em uma só?

O mesmo arquivo, ao mesmo tempo

Dois colegas recebem o mesmo arquivo por e-mail e editam, cada um, um trecho diferente — ao mesmo tempo:

Ana edita a cópia dela
login.js — versão da Ana
function login(user){
if(!user.active) return false;
}
Bruno edita a cópia dele
login.js — versão do Bruno
function login(user){
console.log('login:', user);
}
↓alguém tenta juntar isso à mão…
login.js — tentativa manual de juntar as duas
function login(user){
<<<<<<< versão da Ana
if(!user.active) return false;
=======
console.log('login:', user);
>>>>>>> versão do Bruno
}
Sem uma ferramenta para isso, alguém precisa abrir os dois arquivos e juntar tudo manualmente — lento, chato e fácil de errar.

O contexto: o kernel Linux

Milhares de desenvolvedores, espalhados pelo mundo, escreviam patches de código e os enviavam por e-mail para Linus Torvalds integrar manualmente:

Linus Torvalds

Esse processo manual, feito por e-mail, não escalava — foi exatamente esse gargalo que motivou a busca por uma ferramenta melhor.

Antes do Git: o BitKeeper

2002

Linux passa a usar o BitKeeper, sistema proprietário cedido gratuitamente à comunidade.

2002–2005

Ferramenta funciona bem, mas gera desconforto: código-fonte fechado, dependência de uma empresa.

Abril/2005

Conflito com um desenvolvedor da comunidade leva a BitMover a revogar a licença gratuita.

Resultado: da noite para o dia, o projeto Linux ficou sem ferramenta de controle de versão. Linus Torvalds precisava de uma alternativa — livre, rápida e distribuída.

Nascimento do Git — 2005

Dia 1–3

Linus Torvalds começa a escrever o núcleo do Git do zero.

~10 dias

Versão funcional o suficiente para gerenciar o próprio código-fonte do Git.

Jun/2005

Git já é usado para versionar o kernel Linux em produção.

O nome "Git" é gíria britânica informal — o próprio Torvalds brincou dizendo que segue a tradição de nomear projetos com humor autodepreciativo. Um retroacrônimo popular: "Global Information Tracker".

Antes dos comandos "porcelain"

No início, o Git não tinha os comandos "porcelain" — a interface amigável que usamos hoje (git add, git commit...). Existiam só os comandos de baixo nível, chamados de "plumbing" ("encanamento"): criar um repositório, preparar arquivos e registrar um commit exigia montar isso manualmente, passo a passo:

terminal — como seria em 2006, direto no "encanamento" do Git

Só depois esses passos foram embrulhados nos comandos porcelain que conhecemos: git init, git add e git commit.

Objetivos de Projeto do Git

  • ⚡Velocidade — operações do dia a dia (commit, diff, branch) acontecem localmente, quase instantâneas.
  • 🌐Distribuição — cada cópia do repositório contém o histórico inteiro; não existe um único servidor indispensável.
  • 🔒Integridade dos dados — cada commit é identificado por um hash (SHA) calculado a partir do próprio conteúdo; qualquer alteração muda o hash.
  • 🌿Branches e merges eficientes — criar, alternar e unir ramos deveria ser barato, ao contrário de ferramentas centralizadas da época.

Git como solução

O Git não guarda "arquivos com nomes diferentes" nem exige juntar mudanças à mão. Ele registra a história de evolução de um projeto — um estado registrado de cada vez — e sabe como combinar, de forma confiável, o trabalho de várias pessoas no mesmo arquivo.

É exatamente esse modelo que construímos, peça por peça, na Parte 2.

PARTE 2

Modelo Conceitual do Git

Construindo, passo a passo, o mapa mental que vamos reutilizar até o fim da oficina

Commits são fotografias do projeto

Cada commit representa um estado registrado do projeto em um momento específico — como uma fotografia. Vamos acompanhar isso com um arquivo de texto simples.

arquivo.txt
Olá
C1

Um único commit registrado: o conteúdo "Olá" está gravado permanentemente na história do projeto.

Segundo commit

arquivo.txt
Olá
Git
C1
←
C2

O Git não guarda "um arquivo novo" — ele guarda que, entre C1 e C2, uma linha foi adicionada:

diff C1 → C2
Olá
Git

Terceiro commit

arquivo.txt
Olá
Git
Controle de versão
C1
←
C2
←
C3
diff C2 → C3
Olá
Git
Controle de versão

O Git mantém uma sequência de estados relacionados — a qualquer momento dá para saber exatamente o que mudou entre dois pontos da história.

Commits formando um branch

Uma sequência de commits é o histórico de um branch. Um branch é, na prática, apenas um ponteiro para o último commit — e HEAD aponta para o branch atual.

C1
←
C2
main · HEAD → C2
C1
←
C2
←
C3
main · HEAD → C3

Clique para avançar: um novo commit é criado → o ponteiro main (e HEAD, que aponta para main) se move para o novo commit.

O Modelo: as Quatro Regiões do Git

Este é o diagrama que vamos reutilizar em quase todos os slides daqui em diante. Cada novo comando só vai alterar o estado destas caixas.

  • 1Working Tree — os arquivos como você vê e edita no disco.
  • 2Staging Area (Index) — a "prévia" do próximo commit.
  • 3Repositório Local — o histórico de commits gravado em .git.
  • 4Repositório Remoto — uma cópia hospedada (GitHub, GitLab...).

1Working Tree + git status

Criamos um arquivo. Ele existe no disco, mas o Git ainda não sabe que ele deve fazer parte da história do projeto.

$ git status
Untracked files:
  arquivo.txt
↓efeito no modelo

2git add

$ git add arquivo.txt
↓efeito no modelo

O arquivo continua no Working Tree — apenas uma cópia do seu estado atual passa a existir na Staging Area, preparada para o próximo commit.

3git commit

$ git commit -m "Adiciona arquivo inicial"
↓efeito no modelo

Nasce o commit C1. main e HEAD passam a apontar para ele. A Staging Area volta a "espelhar" exatamente o que está no último commit.

4Editando o arquivo

arquivo.txt (editado)
Olá
Git
↓efeito no modelo

Repare: três versões diferentes convivem agora — Working Tree [Olá, Git], Staging [Olá] e o commit C1 [Olá]. Essa diferença é o coração do modelo do Git.

5git status — de novo

$ git status
Changes not staged for commit:
  modified: arquivo.txt
↓relação direta com o diagrama

"Modified, not staged" é só o Git descrevendo em palavras a diferença entre Working Tree e Staging Area que já víamos no diagrama.

6git diff e git diff --staged

$ git diff

Compara Working Tree × Staging:

Working Tree vs Staging
Olá
Git
$ git diff --staged

Compara Staging × último commit:

Staging vs C1
(sem diferenças — nada novo foi preparado ainda)
Guarde essa regra: git diff olha para a esquerda do modelo (WT↔Staging); git diff --staged olha para o meio (Staging↔commit).

Adicionando o Repositório Remoto

Só depois que o modelo local está bem entendido, adicionamos uma quarta caixa: um repositório hospedado, por exemplo no GitHub, chamado por convenção de origin.

O repositório local está um commit à frente (C3) do remoto — algo muito comum: você commitou localmente, mas ainda não enviou.

7git push

$ git push origin main

Clique para avançar: o commit C3 é replicado para o remoto e o ponteiro origin/main se move até ele.

Git ≠ GitHub

Git

  • ▸É o sistema de controle de versão em si.
  • ▸Roda localmente no seu computador.
  • ▸Funciona sem internet e sem nenhum serviço externo.

GitHub / GitLab / Bitbucket

  • ▸São serviços de hospedagem de repositórios Git.
  • ▸Adicionam colaboração: pull requests, issues, permissões.
  • ▸São, no nosso diagrama, apenas uma forma de repositório remoto.
Dá para usar Git a vida inteira sem nunca abrir o GitHub — e dá para usar GitHub hospedando qualquer coisa versionada com Git.
PARTE 3

Uso Prático do Git

Cada comando, o mesmo diagrama, um novo estado

O Padrão desta Parte

A partir de agora, cada slide segue a mesma estrutura — comando digitado, efeito no terminal, e consequência no modelo conceitual:

$ git add arquivo.txt
↓alteração animada
Working Tree · Staging · Repositório Local · Remoto

comando → resultado → efeito interno no Git

Preparando o Ambiente

Verificar a instalação:

git --version

Configurar identidade (usada em todo commit que você fizer):

git config --global user.name "Seu Nome"
git config --global user.email "seu.email@exemplo.com"
git config --list
A configuração --global vale para todos os repositórios do seu usuário. Sem --global, vale só para o repositório atual.

git init

mkdir meu-projeto && cd meu-projeto
git init
↓efeito no modelo

Cria a pasta oculta .git — o Repositório Local nasce vazio, mas já pronto para receber commits.

git status

echo "Olá" > arquivo.txt
git status
↓efeito no modelo

git status nunca muda o estado — ele só fotografa e descreve o diagrama atual.

git add

git add arquivo.txt
# ou, para todos os arquivos alterados:
git add .
↓efeito no modelo

git commit

git commit -m "Mensagem descrevendo a mudança"
↓efeito no modelo
Mensagens de commit boas descrevem o quê e, se necessário, por quê — quem lê o histórico depois agradece.

git log

git log
git log --oneline
git log --oneline --graph --all
c3f9a2e (HEAD -> main) Adiciona controle de versão
7b1d44a Adiciona linha "Git"
a01e5c0 Adiciona arquivo inicial

git log é a janela para o Repositório Local: mostra exatamente a cadeia C1 ← C2 ← C3 que vimos no diagrama, do mais novo para o mais antigo.

git branch

git branch feature-login
git branch          # lista os branches locais
$ main:
C1
←
C2
←
C3
main · HEAD → C3   ·   feature-login → C3 (recém-criado, aponta para o mesmo commit)
git branch nome apenas cria um novo ponteiro apontando para o commit atual — não copia arquivos, não demora, não "pesa". É por isso que branches no Git são baratos.

git switch / git checkout

git switch feature-login
# forma mais antiga, ainda muito usada:
git checkout feature-login
↓efeito no modelo

O que muda é apenas o que HEAD aponta e o conteúdo copiado de volta para o Working Tree — a seta de volta que vimos no diagrama completo.

git merge

git switch main
git merge feature-login
main: C1 ← C2 ← C3 ←←←←←← M
feature-login: C3 ← C4    ↗

O merge cria um novo commit M que tem dois pais — o último commit de main e o último de feature-login — unindo as duas histórias.

Se ninguém mais mexeu em main desde que o branch foi criado, o Git pode fazer um fast-forward: só empurra o ponteiro de main para a frente, sem criar commit de merge.

git remote e git clone

Ligar um repositório local a um remoto existente:

git remote add origin https://github.com/usuario/repositorio.git
git remote -v

Ou começar já a partir de um remoto:

git clone https://github.com/usuario/repositorio.git
git clone baixa o histórico inteiro e já cria o vínculo origin automaticamente — equivale a criar as quatro caixas do diagrama de uma vez, a partir do remoto.

git fetch vs git pull

git fetch origin   # so atualiza origin/main, sem tocar no seu main
git pull origin main   # equivale a: git fetch + git merge
↓efeito no modelo
git fetch é seguro: só traz novidades do remoto sem mexer no seu Working Tree. git pull vai além — já tenta integrar (merge) essas novidades no seu branch atual.

git push — recapitulando

git push origin main
↓efeito no modelo

Fecha o ciclo completo: add → commit → push. É a mesma seta para a direita, do início ao fim da oficina.

O Diagrama Completo — nos Dois Sentidos

não rastreado modificado preparado sincronizado

Ida: add → commit → push   ·   Volta: fetch/pull e checkout/switch/restore

O Modelo Mental que Fica

Working Tree  — add →  Staging  — commit →  Repositório Local  — push →  Repositório Remoto

A partir deste modelo, comandos como status, diff, add, commit, branch, switch, merge, fetch, pull e push deixam de ser operações isoladas para decorar — e passam a ser movimentos dentro de um mapa que você já entende.
